## Fix and bounded failure behavior

- `scripts/ci_emulator.sh` uses `ANDROID_AVD_HOME=$RUNNER_TEMP/umbra-avds`, creates
  it, supplies `--force --path --device pixel_2 --abi x86_64`, and closes stdin.
- It requires readable/writable KVM and a successful `emulator -accel-check`; launch
  explicitly uses `-accel on`. No software-acceleration fallback.
- Before launch it requires the exact name in `-list-avds`, nonempty registration
  `.ini`, and nonempty `config.ini`. Creation/listing have 60/15-second limits.
- `wait_emulator.py` checks PID/zombie state, `adb devices` and `sys.boot_completed`.
  There is no blind wait-for-device. Each adb command has at most five seconds and
  is bounded by the remaining 180-second boot deadline; late success is rejected.
  Failure prints the emulator log. The 35-minute Android job limit is unchanged.
- EXIT/INT/TERM cleanup owns both PIDs and serials, requests graceful shutdown,
  bounds the wait and escalates termination if necessary. A PID-exit race does not
  abort cleanup or replace an earlier failure. Forced cleanup fails a successful run.
- The Android step finishes single-device connected/offline instrumentation and
  synthetic-signature R8 launch before starting the second AVD. Gradle is no longer
  active. Both AVDs use 1536 MiB guest RAM, two virtual CPUs and a 480×800 display
  to reduce host SwiftShader buffer memory; these settings do not change security.
- `ci_bluetooth.sh` pairs two independent AVDs using Android Settings, compares SSP
  codes, checks both bond tables and runs real production RFCOMM/libsignal for each
  flavor. ADB coordinates pairing/verification, not message transport. Failures
  remain fatal; there is no continue-on-error, skip or TCP substitute. Memory usage
  and pairing/transport diagnostics are retained in the device reports artifact.

## Android CLI evaluation

now recommends the separate Android CLI `android emulator create` command.
CI attempt 2 actually used command-line tools **16.0** installed by the pinned
setup-android action (preinstalled tools **12.0** were rejected by that action).
Local SDK tools **19.0** include avdmanager with explicit path/device/force support;
the separate `android` executable is absent locally. We retain avdmanager already
installed in CI instead of introducing an unverified new CLI/distribution. The
workflow logs CLI availability; success depends on the installed command's output
and emulator discovery, not its nominal exit status alone.
